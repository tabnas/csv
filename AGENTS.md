# Agents Guide — csv

## What this project is

`@tabnas/csv` is a **CSV grammar plugin** for the
[`tabnas`](https://github.com/tabnas/parser) parsing engine. It turns CSV
text into arrays of objects (or arrays of arrays), with headers, RFC 4180
`""`-escaped quoting, custom field/record separators, streaming, and a
strict / non-strict mode.

It is **not** standalone: it layers on the
[`@tabnas/jsonic`](https://github.com/tabnas/jsonic) base grammar (the
relaxed-JSON `val`/`map`/`list`/`pair`/`elem` rules) and reuses the
engine's lexer, comment handling, and streaming hooks. In **strict mode**
(the default) jsonic value parsing is switched off and every field is raw
text; in **non-strict mode** a field body can hold embedded jsonic
(`[1,2]`, `{x:1}`), so the plugin preserves jsonic's default `val`/`elem`/
`list` alternatives.

There are two implementations that must behave identically — TypeScript
(canonical) and a Go port.

## The tabnas engine dependency

Both runtimes depend on the unpublished `@tabnas` siblings via a
**sibling checkout** (the standard tabnas dev model until the packages
publish tagged releases):

- TypeScript: `@tabnas/parser` and `@tabnas/jsonic` are declared as
  `peerDependencies` (`">=2"`) in `ts/package.json` and mirrored as
  `file:../../parser/ts` / `file:../../jsonic/ts` devDependencies for
  local builds. `@tabnas/debug` and `@tabnas/railroad` are dev-only
  `file:` devDependencies (debug for the `debug.model()` test, railroad
  to regenerate `ts/doc/grammar.{svg,txt}`).
- Go: `go/go.mod` requires `github.com/tabnas/jsonic/go` with
  `replace github.com/tabnas/jsonic/go => ../../jsonic/go`. That is the
  module's **only** tabnas dependency — the Go jsonic package re-exports
  the engine types (`jsonic.Make`, `jsonic.Options`, `jsonic.Rule`, …),
  so `csv.go` imports `jsonic`, not `parser`, directly.

Clone the siblings (`parser`, `jsonic`, plus `debug`/`railroad` for the
optional tests) next to this repo and build their TS first. CI does this
for you (see below).

## Authority and alignment rules

**TypeScript is canonical. Go is a port of it.** When you change
behaviour:

1. Change `ts/src/csv.ts` first (or `ts/csv-grammar.jsonic` for grammar
   changes — see the embed section below).
2. Port the same change to `go/csv.go`.
3. Add/extend the shared fixture(s) in `test/fixtures/` + `manifest.json`
   so both runtimes assert the new behaviour. The fixtures are the parity
   contract; both suites resolve them at `../test/fixtures` (TS:
   `ts/test/csv.test.ts`; Go: `go/csv_test.go` `fixturesDir()`).
4. Mirror any new unit cases across `ts/test/csv.test.ts` and
   `go/csv_test.go` — the two unit suites should cover the same ground.
5. Run both suites and confirm green.

Do not let the Go behaviour drift from TS. If Go genuinely cannot match
because of a `jsonic/go` limitation, document the gap here and in the
relevant `doc/*.md` Errors section rather than silently diverging (see
"Known limitations").

## The grammar is embedded — never hand-edit the embedded block

`ts/csv-grammar.jsonic` is embedded verbatim into **both** `ts/src/csv.ts`
and `go/csv.go`, between these markers:

```
// --- BEGIN EMBEDDED csv-grammar.jsonic ---
...
// --- END EMBEDDED csv-grammar.jsonic ---
```

Edit `ts/csv-grammar.jsonic`, then run the embed step. Never edit the text
between the markers by hand — it will be overwritten. (The grammar may not
contain backticks; `embed-grammar.js` aborts if it does, since the Go side
uses a raw string.)

```bash
cd ts && node embed-grammar.js   # writes into ts/src/csv.ts AND go/csv.go
```

`npm run build` runs the embed step first (`node embed-grammar.js && tsc
--build src test`), so a normal TS build keeps both files in sync.

The `csv`, `newline`, `record`, and `text` rules live in the grammar file
(plus the static `rule.start`, `lex.emptyResult`, `error`, and `hint`
options). The `list`, `elem`, and `val` rules are configured **in code
instead** (`tn.rule(...)` in TS / `j.Rule(...)` in Go), because
non-strict mode must preserve jsonic's default alternatives for those
rules so embedded JSON values keep working.

## Architecture notes

- **Strict mode (default).** Jsonic value parsing is disabled; every
  field is raw text, and the plugin's custom RFC 4180 string matcher
  (`buildCsvStringMatcher`) handles `""`-escaped quotes. The JSON
  structural tokens (`#OB`, `#CB`, `#OS`, `#CS`, `#CL`) are switched off,
  and `rule.exclude: 'jsonic,imp'` drops the relaxed alternatives.
- **Non-strict mode** (`strict: false`). Field bodies parse as jsonic, so
  a cell can hold `[1,2]`, `{x:1}`, or a backslash-escaped string.
  Non-strict also defaults `trim`, `comment`, `number`, and `value` to on,
  and excludes only `imp`.
- `#LN` (line end) is removed from the IGNORE token set so row breaks are
  significant; in strict mode `#SP` is also removed so in-field whitespace
  survives.
- Per-instance options are applied **after** `grammar(...)` /
  `j.Grammar(...)`, because Grammar runs an internal `SetOptions` that
  would otherwise clobber the `tokenSet`/`fixed` token overrides.
- The grammar text is parsed by a **separate** engine instance
  (`new Tabnas().use(jsonic).parse(grammarText)` in TS;
  `parseGrammarText` in Go), then handed to `tn.grammar(...)` /
  `j.Grammar(...)` with `{ rule: { alt: { g: 'csv' } } }`. `@`-prefixed
  names in the grammar resolve against the `refs` map (state actions are
  auto-wired by the `@rulename-{bo,ao,bc,ac}` convention; alt actions and
  condition/funcref names are referenced explicitly).
- Token legends: the plugin registers human descriptions for CSV tokens
  via `config.modify` → `cfg.tokenDesc`, which `@tabnas/railroad` reads
  off the live config when drawing the diagram legend.

## Known limitations

- **`field.exact` error code (Go).** TS raises `csv_extra_field` /
  `csv_missing_field` (via `ctx.t0.bad(code)`). `jsonic/go`'s parser does
  not yet propagate a bad token's custom error code — it surfaces every
  `ctx.ParseErr` under the generic `unexpected` code — so the Go error
  currently reports `unexpected`. The port already tags the token with the
  specific code (`ctx.T0.Bad(errCode)`) so parity is automatic once
  `jsonic/go` honours it. Until then, treat a non-nil error from a
  `field.exact` parser as a field-count violation; the Go
  fixture/unit tests assert that the parse fails, not the specific code
  (`go/csv_test.go` `TestFieldExact`).

## Conformance baseline, measured 2026-08-07 — THE SUITE IS RED ON PURPOSE

Phase 1 of the conformance effort built an honest measuring instrument and read
the dial. **No parser source was touched** — `ts/src/csv.ts`, `go/csv.go` and
`csv-grammar.jsonic` are byte-identical to `main`. Fixing the gaps is a later
phase. Do not make these numbers look better by trimming a corpus, loosening an
assertion or adding a skip.

### The claim under test

`README.md`: *"parses CSV text into arrays of objects (or arrays of arrays),
with headers, **RFC 4180 quoting**, custom field/record separators, streaming,
and a strict / non-strict mode."* `ts/doc/concepts.md` adds *"a custom string
matcher that follows RFC 4180"*. There is **no self-limiting qualifier**
anywhere ("a subset of…", "core CSV only"), so the plugin is judged against
**RFC 4180 in full**, in its default strict mode.

### The corpora — fetched, never committed

`scripts/fetch-csv-suites.sh` fetches both at **pinned commit SHAs** into
`test/suites/`, which is gitignored. Only the script and the SHAs are in the
repo. Same pattern as `toml/ts/test/toml-test` and `xml/test/xmlconf`.

| Suite | Upstream | Pinned SHA | Content |
|---|---|---|---|
| csv-spectrum | `max-mapper/csv-spectrum` | `d30e80f8b99d2eecb3778f1d7b9ed1cb425502ec` | 12 documents, **valid only** |
| go/encoding/csv | `golang/go` `src/encoding/csv/reader_test.go` (tag `go1.24.0`) | `3901409b5d0fb7c85a3e6730a59943cc93b2835c` | 68 readTests → 55 cases: **43 valid + 12 must-fail** |

**Why the Go standard library.** csv-spectrum is the most-cited third-party CSV
corpus and it has *no must-fail half at all*. The W3C csvw suite has 145
`NegativeValidationTest` entries, but the number of them whose action is a bare
`.csv` syntax violation is **zero** — every one is a JSON-LD metadata/schema
violation (checked against `tests/manifest-validation.jsonld`). The Go standard
library's `encoding/csv` table is the reference RFC 4180 implementation's own
conformance table, is third-party, is release-tagged, and carries explicit
expected **errors** (`ErrQuote`, `ErrBareQuote`, `ErrFieldCount`). It is the
closest thing to an authoritative must-fail CSV corpus that exists.
`scripts/extract-go-csv-cases.mjs` converts it to a runtime-neutral
`cases.json`, and **aborts** if the case counts drift from the pinned
expectation, so the corpus cannot silently shrink.

Two groups of readTests are excluded, both counted and asserted by
`TestGoEncodingCsvExcluded` / `the excluded set is exactly the documented one`
so the set cannot quietly grow:

- **`LazyQuotes: true`** (5) — a deliberately non-RFC-4180 lenient mode with no
  `@tabnas/csv` equivalent, so there is no behaviour to assert either way.
- **no `Input` at all** (8, the `errInvalidDelim` group) — they assert that Go's
  `NewReader` rejects a bad `Comma`/`Comment` *rune*. An API validation test,
  not a document.

**The suite cannot skip.** `ts/package.json` has a `pretest` hook that runs the
fetch script, and `go/conformance_test.go`'s `ensureCorpus` runs it itself when
the corpus is absent; if the corpus is *still* missing both halves fail with a
loud message and **never** call `t.Skip` / `it.skip`. `make test` also fetches
first. (The repo's CI is the shared reusable workflow
`tabnas/.github/.github/workflows/polyglot-ci.yml@main`, which cannot be edited
from this repo — the `pretest` hook and `ensureCorpus` are what make the fetch
happen inside it.)

csv-spectrum's 12th document, `location_coordinates`, is **defective upstream**

its own `.csv` (`2095257564`) — the JSON was scrubbed and the CSV was not. It is
**pinned, not excluded**: `TestCsvSpectrumUpstreamDefect` asserts both halves of
the contradiction, so if upstream fixes either the test goes red and the case
returns to the judged set.

### Gap 1 — `'` and `` ` `` are still live string delimiters in TS strict mode

RFC 4180 `TEXTDATA` is `%x20-21 / %x23-2B / %x2D-7E`, which includes both `'`
(0x27) and `` ` `` (0x60): they are ordinary field content. In strict mode the
plugin swaps in its own RFC 4180 `"`-matcher but leaves the **engine's other
default string delimiters** active, so TypeScript eats them:

```js
new Tabnas().use(jsonic).use(Csv).parse("a\n'b'")    // [{a:'b'}]      WRONG (Go: [{a:"'b'"}])
new Tabnas().use(jsonic).use(Csv).parse("a\n'b")     // throws unterminated_string on a LEGAL document (Go: [{a:"'b"}])
new Tabnas().use(jsonic).use(Csv).parse('a\n`x`')    // [{a:'x'}]      WRONG (Go: [{a:"`x`"}])
```

The Go port gets all three right. Over an exhaustive 2401-input sweep
(`scripts/probe-sweep.mjs`, alphabet `a , " \n ' \`` ` and space, length 4) this
one defect accounts for **~1050 of the 1073 TS/Go divergences**.

### Gap 2 — quoting violations accepted rather than rejected (BOTH runtimes)

Both runtimes invent a value where RFC 4180 and `encoding/csv` reject:

| input | TS + Go produce | RFC 4180 |
|---|---|---|
| `a,b\nx"y,2` | `x"y` | DQUOTE is excluded from `TEXTDATA` (`BadDoubleQuotes`, `BadBareQuote`) |
| `a,b\n"1" ,2` | `1 ` | only COMMA/CRLF may follow a closing DQUOTE |
| `"a word",b"` | `b"` | bare DQUOTE in a `non-escaped` field (`BadTrailingQuote`) |
| `"field"\r\r` | `field` | `QuotedTrailingCRCR` |

### Gap 3 — a quoted field ending in `""` at EOF (TS accepts, Go rejects)

`a\n"""` — DQUOTE, an escaped `2DQUOTE`, then EOF with no closing DQUOTE. TS
returns `[{a:'"'}]`; Go and the `encoding/csv` oracle both reject. 14 sweep
inputs are in this class (`"a""`, `,"""`, `\n"""`, …). TS is canonical but is
wrong here; `OddQuotes` in the Go corpus is the same case.

### Gap 4 — `field.exact` is silently a no-op unless `object` records are built

```js
parse('a,b,c\nd,e', { field:{exact:true} })                                 // throws csv_missing_field   correct
parse('a,b,c\nd,e', { object:false, field:{exact:true} })                   // [["d","e"]]                NO ERROR
parse('a,b,c\nd,e', { header:false, object:false, field:{exact:true} })     // [["a","b","c"],["d","e"]]  NO ERROR
```

This is why `BadFieldCount` / `BadFieldCountMultiple` are in the invalid-half
failures. (`BadFieldCount1` additionally sets Go's `FieldsPerRecord: 2`
explicitly, which has no `@tabnas/csv` analogue at all — it is left in the
corpus and left red rather than removed.)

### Gap 5 — Go `Use(Csv, nil)` does not apply the plugin defaults

`j.Use(Csv, nil)` yields `[["a","b"],[1,2]]` for `a,b\n1,2` — header row kept,
rows as arrays, non-strict number coercion — where TS's `use(Csv)` yields
`[{a:"1",b:"2"}]`. Only `j.UseDefaults(Csv, Defaults)` matches TS. Pinned as a
characterisation test in `go/csv_test.go` `TestUsePlugin`, which previously
asserted nothing at all and so hid this.

### NOT a jsonic-layering leak

The suspected json5-shaped defect (plugin alone rejects what the documented
`use(jsonic).use(X)` stack accepts) **does not occur here in strict mode**. Over
the same 2401-input sweep, `new Tabnas().use(jsonic).use(Csv)` and
`new Tabnas().use(Csv)` agree on **2401/2401** inputs — including
`"a\n'b'"` → `[{a:'b'}]` from both. The leniency in Gap 1 comes from the
*engine's own default string options* in `@tabnas/parser`, not from stacking the
jsonic base grammar. In `strict:false` mode `use(jsonic)` genuinely is required:
the plugin alone accepts 0/4 of `a\nb`, `a\n[1,2]`, `a\n{x:1}`, `a\n1`.

## Build & test

TypeScript (from `ts/`):

```bash
npm install            # auto-installs peers; resolves file: siblings
npm run build          # embeds grammar, then tsc --build src test
npm test               # node --test over dist-test/*.test.js
```

Go (from `go/`):

```bash
go build ./...
go test -v ./...       # unit tests + shared fixtures
```

The repo root [`Makefile`](Makefile) wraps both: `make build|test` run
the TS and Go halves, and `make publish-go V=x.y.z` injects `V` into the
`const Version` in `go/csv.go` (currently `0.1.4`) and tags `go/vX.Y.Z`.
The TS package version is `0.11.0` (`ts/package.json`).

Local builds resolve the unpublished siblings via the repo-set
`go.work` + node_modules symlinks created by `admin/scripts/link.sh`;
there is no checked-in `go.work` in this repo.

## Optional tests (@tabnas/debug)

`ts/test/debug-model.test.ts` composes the csv plugin with the external
`@tabnas/debug` plugin and asserts the structured grammar model: the rule
set (`csv`, `record`, `text`, `newline` plus the shared jsonic
`val`/`map`/`list`/`pair`/`elem`), `m.config.start === 'csv'` (note
`config.start`, not `m.start`), that `Csv` is in `m.plugins`, and that
`csv` pushes `newline`/`record` while `record` pushes `list`. It resolves
debug dynamically and **skips** unless `@tabnas/debug` is installed (it is
a `file:` devDependency, so `npm test` runs it) or `TABNAS_DEBUG_PATH`
points at a built sibling.

`ts/test/doc-examples.test.ts` extracts fenced `js` blocks containing
`// =>` assertions from the README and docs and runs them — keep doc
examples correct.

## CI

`.github/workflows/build.yml` has two jobs, neither publishing to npm:

- **build** (Ubuntu/Windows/macOS, Node 24): sets
  `git config --global core.autocrlf false` (CRLF corrupts the `.csv`
  fixtures, which are marked `binary` in `.gitattributes`), git-clones the
  tabnas closure (`parser debug json abnf railroad jsonic`) as siblings,
  `npm i && npm run build` each in topo order, then `npm test` here.
- **build-go** (Ubuntu/macOS, Go 1.24): clones the same siblings, mirrors
  `admin/scripts/link.sh` by creating `vendor/` symlinks for any
  `../vendor/` replaces and a `go work` over every non-vendor-replaced
  module, then `go build`/`go test -v` here.
